# Implementation note

**Design.** FastAPI serves a plain HTML/JavaScript interface using Bootstrap controls, Bootstrap Icons and locally bundled IBM Plex Sans. Literal workflow navigation and a linked requirements index expose the required functions. SQLite stores customers, visits, quotes, messages, schedules, business rules, delivery keys, and the activity trail. A shared adapter uses the official Anthropic SDK for Claude by default and LiteLLM for other providers. Pydantic validates decisions. Provider, model, endpoint, credentials, and schema/JSON mode are configurable. APScheduler handles recurring dates and background polling; Python’s SQLite and timezone libraries supply storage and local time. No custom model client, intent classifier, or recurrence parser is used. Guided demo is a deterministic collection of sample inputs for exploring the app without an API key.

**Booking and control.** Each conversation is serialized within the single app process. AI calls happen outside database transactions. Python writes each accepted action under `BEGIN IMMEDIATE`, checking current opening rules, the slot grid, technician overlap, and customer overlap before committing a visit. Confirmations are rendered from committed data. Saved gate codes are copied onto appointments. Owner instructions update opening days and facts. Handoffs retain a concise summary, pause automatic customer messages, and stay paused until the owner resumes them. Booking, rule, and handoff events link back to the message that triggered them.

**Scheduled work.** Daily or weekly reports use APScheduler cron triggers. The SQLite cursor lets a five-second background job catch up after a restart or demo-clock jump. Inserting a unique delivery key, message, and activity event in one transaction prevents repeated simulated deliveries. Reminders run the day before a visit, including appointments booked after the morning sweep. Quote follow-ups require a sent quote and three quiet days, stop after resolution, and pause during a handoff. “Waiting on a quote” always means the shop owes the customer an estimate.

**Assumptions and cuts.** One business, one server process, a configurable same-day opening window, fixed visit duration, and equally qualified technicians. Returning identity comes from the demo customer selector. Messaging and calendars are local simulations. No login, travel-time optimization, real dispatch, pricing engine, cancellation/rescheduling flow, or arbitrary workflows. Reports support daily or single-weekday recurrence at a local hour and minute. Catch-up reports summarize the available records rather than reconstructing historical snapshots. PostgreSQL records scoped by tenant and a durable queue with delivery retries are the intended larger-scale replacements; external messaging would use an outbox and provider idempotency.

**AI-tool use.** Coding assistance produced and reviewed the implementation, documentation, and workflow checks. Official SDK and APScheduler references informed the integrations. Runtime AI is limited to interpreting conversation turns with supplied business/customer context; application code performs mutations. The no-key walkthrough uses fixtures and makes no model calls.

**Verification.** Sixteen focused workflow and provider checks passed, covering returning and new customers, competing bookings, stale Sunday offers, handoff/resume, quote lifecycle, reminder/report delivery, restart deduplication, recurrence, and provider validation. The internal browser walkthrough used live Claude with fictional records to book a visit, retain the saved address and gate code, hand off a refund request, send an owner reply, close Sundays, and schedule a Friday quotes-owed report. It exposed omitted structured fields and a generic handoff summary; requiring all wire fields and retaining the original request as a summary fallback corrected both. Docker startup, health, persisted records, local UI assets, documentation routes, and JavaScript syntax were verified. Desktop and narrow-screen navigation were inspected.
